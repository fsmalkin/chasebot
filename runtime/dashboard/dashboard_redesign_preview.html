Chasecar Dashboard — First Principles

Goals, stories, and design decisions before touching CSS.

1

Prove the work

Someone watching — a PM, a demo audience, a teammate — needs to confirm at a glance that the robot behaved correctly. They do not need to know about Docker, ROS, or LLM internals to get value from this view.

watchI can see whether the current proof run is in progress, passed, or failed without reading any numbers.
watchI can see the robot's camera feed and the YOLO detection feed live, side by side.
watchI can see which stage of the proof we are in (searching → approaching → done) as a simple progress arc, not a log file.
watchI can start the environment and launch a demo scenario with two clicks and nothing else.
2

Be the LLM

An operator or engineer wants to understand (and verify) the LLM's decision loop by stepping through it manually. They should see exactly what the LLM sees — no more — and choose from exactly the same constrained set of actions.

driveI can see the three facts the LLM uses to decide: is the target visible, how far away, and is a nav goal currently in flight.
driveI can choose from the same small intent list the LLM uses (acquire, plan, track, abort) as large, obvious buttons.
driveThe interface shows me which action the LLM would have chosen (highlighted, not forced) so I can agree or override.
driveAfter I dispatch an action I can see immediately whether the robot responded (nav accepted, cmd_vel seen).
3

See behind the scenes — minimally, in layers

A developer debugging a failure needs to drill into the underlying signals without cluttering the view for everyone else. Visibility should be progressive: surface → LLM reasoning → raw telemetry.

inspectLayer 1 (surface): I can see what the robot is doing right now in one sentence — e.g. "turning to find ball, 3rd attempt".
inspectLayer 2 (LLM): I can see the last intent the LLM issued, the reason it gave, and whether the preview gate passed or blocked it.
inspectLayer 3 (signals): I can see the raw perception and outcome values (visible ratio, distance, cmd_vel, nav_goal_recent) if I want them.
inspectLayers 2 and 3 are collapsed by default and do not take up space unless I open them.
Design decisions that follow
Three modes, not three panels. Watch / Drive / Inspect are different jobs. Showing all three at once makes the busiest job dominate the layout. A tab switches the entire content area.
Status in one sentence, not four pills. A colored dot + one phrase ("searching for ball · attempt 3") communicates more than four separate status fields the reader has to synthesize.
Drive mode shows only what the LLM sees. If the LLM only gets target_visible, distance, and goal_in_progress, then the manual control UI should show only those three facts. Everything else is a distraction from the job of mimicking the model.
Controls live in the sidebar only in Drive mode. In Watch mode, controls are irrelevant. In Inspect mode, the user is reading, not acting. Surfacing environment/scenario buttons everywhere implies they are always relevant — they are not.
Progressive disclosure via accordion, not drawer. A slide-out drawer is a context switch (the main content disappears). An accordion within the Inspect tab lets the user compare a collapsed summary with expanded detail without losing their place.
